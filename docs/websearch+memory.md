## 一、联网搜索模块（Search Engine）

### 1.1 架构设计

```
┌─────────────────────────────────────────────────────────────┐
│                      搜索意图解析层                           │
│  用户Query → 意图分类 → 时效性判断 → 搜索策略选择              │
├─────────────────────────────────────────────────────────────┤
│                      多源搜索执行层                           │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐      │
│  │ 通用搜索  │ │ 学术搜索  │ │ 新闻搜索  │ │ 垂直搜索  │      │
│  │(Google/  │ │(Google   │ │(实时新闻  │ │(电商/代码 │      │
│  │ Bing API)│ │ Scholar) │ │ API)     │ │ /法律)   │      │

├─────────────────────────────────────────────────────────────┤
│                      结果融合与验证层                         │
```

### 1.2 核心优化策略

#### A. 搜索意图智能路由

```python
# 意图分类决策树
def route_search(query, user_context):
    if contains(query, ["最新", "今天", "刚刚", "news"]):
        return "news_search"      # 实时新闻源
    elif contains(query, ["论文", "研究", "学术", "paper"]):
        return "academic_search"  # Google Scholar/ArXiv
    elif contains(query, ["价格", "购买", "评测"]):
        return "commerce_search"  # 电商/评测网站
    elif contains(query, ["代码", "bug", "API", "github"]):
        return "code_search"      # GitHub/StackOverflow
    elif is_personal(query, user_context):
        return "memory_first"     # 先查个人知识库，不足再联网
    else:
        return "general_search"   # 通用搜索
```

#### B. 时效性感知搜索

| 查询类型 | 时间权重 | 搜索策略 |
|---------|---------|---------|
| "最新iPhone价格" | 极高（<7天） | 强制刷新缓存，优先新闻/电商源 |
| "React最新特性" | 高（<3个月） | 搜索官方文档 + 近期技术博客 |
| "二战历史" | 低 | 使用缓存结果，优先权威百科 |
| "昨天你说..." | 无 | 直接查询本地记忆，不联网 |

#### C. 多源结果融合算法

```
评分维度：
- 来源权威性（域名权重：.edu > .gov > 知名媒体 > 博客）
- 内容新鲜度（发布日期）
- 与用户历史兴趣匹配度
- 内容完整性（是否直接回答，而非标题党）

融合公式：
Final_Score = 0.3*Authority + 0.25*Freshness + 0.25*Relevance + 0.2*Personal_Match
```

#### D. 搜索结果与记忆关联

```
搜索流程增强：
1. 用户问："推荐一款适合我的耳机"
2. 系统先检索记忆："用户偏好 → 喜欢低音、预算500元、之前买过索尼"
3. 搜索Query自动增强："500元 低音好 耳机推荐 索尼对比"
4. 返回结果时标注："基于你之前喜欢的索尼风格，这款..."
```

### 1.3 可信度与事实核查

| 机制 | 实现方式 |
|-----|---------|
| 交叉验证 | 同一事实需至少2个独立来源确认 |
| 来源标注 | 每个事实句末尾标注 `[来源: xxx]` |
| 不确定性表达 | 无法核实时说"根据部分来源..."而非断言 |
| 用户纠错 | 用户说"不对，实际是..." → 记录修正并降低该来源权重 |

## 二、记忆模块（Memory System）

### 2.1 三层记忆架构

```
┌─────────────────────────────────────────────────────────────┐
│  🧠 工作记忆 (Working Memory)                                │
│  容量：最近5-10轮对话                                        │
│  作用：维持上下文连贯性                                       │
│  技术：对话窗口 + 摘要压缩                                    │
├─────────────────────────────────────────────────────────────┤
│  📅 情景记忆 (Episodic Memory)                               │
│  容量：数月内的对话事件                                       │
│  作用："上周三你提到要面试"                                   │
│  技术：时间戳 + 事件图谱 + 向量检索                           │
├─────────────────────────────────────────────────────────────┤
│  🏛️ 语义记忆 (Semantic Memory)                               │
│  容量：长期稳定的知识/偏好                                    │
│  作用："用户是程序员、喜欢爵士乐、对猫过敏"                    │
│  技术：知识图谱 + 结构化数据库                                │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 记忆提取与存储流程

```
每次对话结束后自动执行：

对话文本
    ↓
[1] 关键信息提取（LLM Prompt）
    ↓
提取结果：
  - 事实型："用户养了只叫橘子的猫" → 语义记忆
  - 事件型："用户今天提交了辞职申请" → 情景记忆
  - 情感型："用户提到最近很焦虑" → 情感记忆（带情绪标签）
    ↓
[2] 重要性评分（1-10分）
    - 涉及身份/家庭/健康 → 9-10分
    - 临时偏好/日常琐事 → 3-5分
    - 已确认的旧信息重复 → 1-2分（去重）
    ↓
[3] 冲突检测
    - 新记忆："用户现在喜欢狗"
    - 旧记忆："用户对猫过敏"
    → 不冲突，并存
    - 新记忆："用户现在不喜欢爵士了"
    - 旧记忆："用户喜欢爵士乐"
    → 标记待确认，或更新时间戳
    ↓
[4] 存储入库
    - 高重要性 → 立即持久化
    - 低重要性 → 暂存区，积累后批量处理
```

### 2.3 记忆的数据结构

```json

```

### 2.4 记忆检索策略

```
用户输入新Query时：

Step 1: 语义检索
  Query向量化 → 向量数据库相似度搜索 → 召回Top-K记忆

Step 2: 时序检索
  如果Query含时间词（"上周"、"上个月"）→ 按时间范围过滤

Step 3: 关联检索
  从召回的记忆出发 → 图谱遍历找关联记忆
  例：召回"用户喜欢咖啡" → 关联出"用户有台手冲壶"、"用户讨厌速溶"

Step 4: 重要性加权
  最终排序 = 语义相似度 × 重要性分数 × 时间衰减因子
  时间衰减：越久未访问的记忆权重越低（但核心身份记忆不衰减）

Step 5: 上下文注入
  将筛选后的记忆注入System Prompt：
  "用户背景：...；近期事件：...；当前情绪：..."
```

### 2.5 记忆遗忘机制

| 遗忘类型 | 触发条件 | 处理方式 |
|---------|---------|---------|
| 自然遗忘 | 低重要性 + 长期未访问 | 权重衰减至阈值后归档 |
| 主动遗忘 | 用户说"忘掉..." | 立即删除或标记失效 |
| 纠错遗忘 | 用户纠正旧信息 | 旧记忆标记`superseded_by: new_id` |
| 矛盾遗忘 | 新记忆与旧记忆冲突且置信度更高 | 旧记忆降级，新记忆标记`revised` |

### 2.6 记忆与搜索的协同

```
协同场景示例：

用户： "我上次说的那个项目怎么样了？"

系统处理：
1. 记忆检索 → 找到："用户5月10日提到在做一个AI项目，叫'智聊'"
2. 判断时效性 → 需要最新进展，触发搜索
3. 搜索Query构建 → "智聊 AI项目 最新进展"（结合记忆上下文）
4. 如果搜索无结果 → 回退询问："你指的是哪个项目？是智聊吗？"
5. 如果搜索有结果 → 结合记忆个性化回答：
   "你之前做的智聊项目，最近我看到有类似产品上线了，
    不过你的版本有记忆模块这个差异化功能..."
```

## 四、关键技术实现建议

### 记忆模块技术选型

| 组件 | 推荐方案 | 理由 |
|-----|---------|------|
| 向量数据库 | Chroma / Milvus | 开源、支持元数据过滤 |
| 结构化存储 | PostgreSQL + JSONB | 关系+文档混合，查询灵活 |
| 记忆提取 | 专用Prompt + 小模型 | 成本低，可本地运行 |
| 知识图谱 | Neo4j / 自研轻量版 | 关系推理，关联记忆 |
| 时序处理 | TimescaleDB扩展 | 天然支持时间范围查询 |

### 搜索模块技术选型

| 组件 | 推荐方案 |
|-----|---------|
| 通用搜索 | SerpAPI / Bing API / 自建爬虫 |
| 学术搜索 | Semantic Scholar API / ArXiv API |
| 结果摘要 | 专用摘要模型（如BART）或LLM |
| 可信度评分 | 域名黑名单 + PageRank近似 + 用户反馈 |
