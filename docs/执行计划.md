# SunChat 个人助理 – 可追踪、可持续维护的执行计划

> **文档目的**
> - 将《SunChat 个人助理优化方案》拆解为可执行的工作项
> - 为每个工作项指明 **负责人、时间窗口、依赖、交付物、验收标准**
> - 给出 **追踪方式（GitHub Projects / Issue Board）** 与 **后期维护流程**，确保计划在实现后仍然可演进

> **整体节奏**（假设 1 人·全职、每周 40 h）
> - **第 1–2 周** – P0（记忆语义检索、知识库解析、对话记忆注入）
> - **第 3–4 周** – P1（记忆自动提取、搜索答案整理、搜索记忆上下文）
> - **第 5–6 周** – P2（对话路由、搜索历史关联、流式 SSE）
> - **第 7–9 周** – P3（前端 UI 完善、状态轮询、来源卡片）
> - **第 10 周** – 安全强化、Docker化、文档与回顾

> **里程碑**
> - **M1（第 2 周末）** – 记忆语义检索 + 知识库解析 + 对话注入全部通过单元/集成测试
> - **M2（第 4 周末）** – 自动记忆提取、搜索答案整理、记忆‑搜索上下文完成
> - **M3（第 6 周末）** – 对话路由、搜索历史、SSE 实现并在本地可演示
> - **M4（第 9 周末）** – 前端 UI 全面升级、状态轮询、来源卡片上线
> - **M5（第 10 周末）** – 安全、Docker、文档、回顾、交付生产准备

## 1️⃣ 追踪体系

| 工具 | 用途 | 说明 |
|------|------|------|
| **GitHub Projects (Kanban)** | 所有工作项（Issue）在看板上流转：`Backlog → To‑Do → In‑Progress → Review → Done` | 每个工作项对应唯一 Issue（见下表），使用标签 `P0 / P1 / P2 / P3`、`backend / frontend / infra` |
| **Milestones** | 与里程碑 M1–M5 对应，自动汇总对应 Issue 的完成进度 | 每个 Issue 必须关联对应 Milestone |
| **GitHub Actions** | CI / CD（单元测试、Lint、类型检查） | 所有代码提交必须通过 `ci.yml`，否则无法合并 |
| **CHANGELOG.md** | 记录每次发布的功能、破坏性改动 | 自动生成（使用 `git-chglog`） |
| **Documentation folder** (`docs/`) | 设计文档、架构图、运行手册 | 每次功能实现后同步更新对应章节 |
| **Runbook / Ops** (`ops/`) | 部署、监控、日志、灾难恢复流程 | 交付时统一放入 `ops/` 目录 |

> **使用流程**
> 1. **创建 Issue**（参见下表） → 关联 **Milestone** 与 **标签**。
> 2. 开发分支 `feature/<ID>` → PR → 通过 **CI** → **Review** → 合并。
> 3. 合并后自动移动 Issue 到 **Done**，里程碑进度更新。
> 4. 每周例会（30 min）回顾看板，更新 **状态**、**风险**、**阻塞**。

## 3️⃣ 维护与演进流程

| 步骤 | 说明 | 负责方 |
|------|------|--------|
| **1. 日常监控** | - 通过 `ops/monitoring.md`（Prometheus + Grafana）监控 `uvicorn`、`npm`、Ollama、Chroma；<br>- 报警阈值：CPU > 80 %、内存 > 75 % 或 LLM 调用错误率 > 5 % | DevOps |
| **2. Bug Triage** | - 每周一次 Bug Review Meeting（15 min）<br>- 将新 bug 归类到 `Backlog`（标签 `bug`），优先级评估后分配 | QA / Dev |
| **3. 版本发布** | - 每 **两周**（Sprint）生成一次 **Release Candidate**（标签 `vX.Y.Z`）<br>- 自动生成 `CHANGELOG`、更新 `README`、发布 Docker 镜像 | Release Engineer |
| **4. 文档同步** | - 代码变更后必须更新对应 **Docs**（Architecture、API、Runbook）<br>- CI 检查文档链接是否失效（`markdown-link-check`） | Docs Owner |
| **5. 技术债务管理** | - 每月一次技术债务评审，将 > 30 % 覆盖率、未使用的依赖、性能热点记录为 **Technical‑Debt** Issue | Tech Lead |
| **6. 回顾 & 规划** | - 每 **Sprint** 结束时进行 **Retro**（What went well / What can improve / Action items）<br>- 将 Action items 写入 `Backlog`，更新里程碑 | Scrum Master |

## 4️⃣ 示例 Issue（GitHub）创建模板

```markdown
**Title:** T001 – 记忆向量库初始化 & 双写  
**Labels:** P0, backend, enhancement  
**Milestone:** M1 – 记忆语义检索 + 知识库解析 + 对话注入  

### Description
- 在 `memory_service.py` 中创建 Chroma client（persist_directory=`./data/chroma_memories`）。
- 为 `MemoryService.create_memory` 添加双写逻辑：先写 SQLite，再生成向量写入 Chroma。
- 实现 `MemoryService.search_memories` 使用向量检索并返回相似度。
- 添加单元测试 `tests/test_memory_vector.py`，覆盖创建、检索、错误回滚。

### Acceptance Criteria
1. `create_memory` 成功写入 SQLite 与 Chroma（在两者中都能查询到相同记录）。
2. `search_memories` 返回 `id, content, similarity`，相似度为 `0–1` 范围。
3. 所有单元测试 `pytest -q` 通过，覆盖率 ≥ 80 %。
4. 文档 `docs/memory_vector.md` 更新，包含使用说明与示例。

### Tasks (checklist)
- [ ] 初始化 Chroma client（persist dir）
- [ ] 修改 `Memory` model（若需新增字段）
- [ ] 实现双写逻辑
- [ ] 编写向量检索函数
- [ ] 编写单元测试
- [ ] 更新文档
- [ ] CI 通过
```

> **同理**，其他任务使用类似模板，确保 **描述、验收、任务列表** 明确。
